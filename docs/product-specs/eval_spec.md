# AI评估标准与机械化执行规范 (Harness Evaluation)

本文件定义了系统在 Harness Engineering 体系下的“机械化执行 (Mechanical Enforcement)”标准。
每次提交 (PR) 前，智能体必须通过自动化脚本验证其输出是否符合以下约束。

## 1. 计划生成评估 (Planner Evaluation)

**规则判定 (Rule-based Linter)**:
- [ ] **格式验证**: 输出必须为完全合法的 JSON 格式。
- [ ] **数量约束**: 任务数量严格控制在 3 到 5 个之间（超出视为失败，触发拦截）。
- [ ] **要素检查**: JSON 字段中必须包含“休息”相关安排。
- [ ] **完成标准**: 每个任务节点必须包含明确的、可验证的“完成标准”字段。

**模型打分 (LLM-as-a-Judge)**:
- 任务难度是否循序渐进，是否符合用户当天的精力状态？

## 2. 复盘评估 (Coach Evaluation)

**规则判定 (Rule-based Linter)**:
- [ ] **数据验证**: 必须包含精确的数值化“完成率”字段。
- [ ] **分析维度**: 必须包含对未完成任务的具体分析。
- [ ] **行动建议**: 必须包含至少一条针对明日计划的行动建议。

**模型打分 (LLM-as-a-Judge)**:
- 教练的语气是否具有同理心和鼓励性？是否能让用户建立教练依赖感？

## 3. 代码与接口评估 (Code & Interface Evaluation)
*用于防范技术债，维护“代码库免疫系统”*

**规则判定 (Rule-based Linter)**:
- [ ] **Hashline 协议验证**: 如果 Agent 尝试修改文件，是否使用了规范的内容寻址协议（例如正确的行号+哈希标签格式）？
- [ ] **坏味道拦截 (Bad Pattern Blocker)**: 通过自定义 Linter (如 AST 解析) 检查是否存在已知的不良实现模式（如硬编码、越权访问 Service 层等），一旦发现立即阻断。

## 4. 不合格拦截 (Hard Failures)
*触发以下任何一条，即意味着智能体生成的反馈或代码需要丢弃并自我纠正（Self-Correction）：*
- 输出非 JSON 或 JSON 解析失败（将自动把解析错误抛回给 Agent 重试）。
- 任务过多（>5个，导致用户心理负担过重，违反核心愿景）。
- 无完成标准（无法进行机械验证）。
- 触发了“代码库免疫系统”中的核心红线规则（如未遵循接口协议或引入已知技术债）。
